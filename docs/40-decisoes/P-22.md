# P-22 — A unicidade da fatura por OCS/PSA não é garantida pelo banco

A regra de negócio é clara: **uma fatura é única para cada par `(pacote, OCS/PSA)`**. É essa
regra que permite detectar o [[Bug do protocolo]].

`PacotesController::store()` a implementa em PHP, verificando duplicidade antes de criar. Mas
`numero_fatura` na tabela `pacotes` é apenas `string`, **sem índice, sem constraint**.

## Consequência

Qualquer escrita que não passe por `store()` recria o problema sem encontrar resistência:
importação de dados, correção manual via `tinker` (prática documentada na
[[Sobre a especificação original|especificação original]]), um endpoint futuro, um seeder.

E, sem índice, a própria consulta de detecção varre a tabela inteira.

## Correção

Não é só adicionar `unique` — a base atual **já tem violações** ([[P-21]]), então um
`unique` falharia na migration. A ordem correta:

1. Investigar e corrigir os dados existentes —
   [`specs/001-caca-bug-protocolo/`](../../specs/001-caca-bug-protocolo/spec.md).
2. Decidir o comportamento para pacotes **anulados**: hoje `store()` os ignora
   deliberadamente na verificação (um pacote anulado libera o número da fatura para
   reuso). Um `unique` simples quebraria isso — a solução é um índice único
   **parcial/condicional**, ou um índice comum mais a validação de aplicação mantida.
3. Só então criar o índice.

O passo 2 é o que faz esta pendência não ser trivial: a regra de negócio real é "única entre
pacotes **ativos**", e MySQL não tem índice único parcial nativo. As opções são uma coluna
gerada, um índice comum com a validação em PHP como hoje, ou um trigger.

Ver [[Modelo de dados]] e [[P-21]].
